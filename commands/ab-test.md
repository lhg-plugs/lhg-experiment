# /lhg-experiment:ab-test —— A/B 测试专项

用户输入在 `$ARGUMENTS` 中：实验目标一句话。面向线上产品实验（加载 exp-design 第 4 节 + result-read）。

## 流程

### 1. 分流方案
- 分流键：用户 id 哈希（登录态）/ 设备 id（未登录）；分流层级写进 plan。
- 分流比默认 1:1；要非均分（如 9:1 灰度）必须写理由（风险控制/流量限制）。
- **SRM 检查**：开跑 24 小时内做一次样本比例不匹配检查，分流 bug 会让整个实验作废。

### 2. 时长规划
- 至少 1 个完整业务周期（通常 7 天，含周末）；流量小就延长，不许缩短。
- 新奇效应/学习期：上线前 2~3 天数据只看不判。
- 提前定好"跑满 X 天或达到 N 样本先到为准"，**中途不许看 p 值做停止决策**。

### 3. 功效测算
走 `/lhg-experiment:power` 流程，结果写入 plan.json。

### 4. 显著性判定与解读（实验跑完后）
按 result-read 四步走：
1. 先看主要指标的 p 值（显著性：是不是噪音）
2. 再看效应量（值不值得做）
3. 再看置信区间（效果的可能范围）
4. 最后谈业务意义（换算成钱/用户数）

多指标 → Holm/Bonferroni 校正；分组洞察 → 标"探索性"，另起实验验证。

### 5. 跑审计
```bash
python3 ${CLAUDE_PLUGIN_ROOT}/scripts/audit/experiment_audit.py --target <实验目录> --format text
```
blocker（如偷看提前停、多重比较未校正）必须处理：要么重跑，要么在报告里如实声明局限。

## 输出
`ab-test-plan.md` + `ab-test-report.md`（报告模板：数据表 / 四步解读 / 局限声明 / 决策建议）。

## 硬规则
- "跑两天看看，显著就全量" → 直接拦截，这是最典型的 p-hacking。
- 报告里出现"显著"却没有效应量 → 打回重写。
